# PROGRAM: 1:1 high-poly aircraft models (aircraft-models)

Owner request: *"bomber models and plane models need to look like the real thing they are too basic
currently. can you make some 1 to 1 models that are accurate with correct views. research then implement.
would it be better to make them in blender first?"* — plus **"must be high poly count"**.

Owner decisions (2026-10-10):
- **Pacing:** straight through all 24 spec'd aircraft, no interim sign-off. Verification = the repo test
  gate + rendered orthographic sheets (front/side/top) + in-game renders, kept as an evidence trail.
- **Shading:** keep the game's toon look — high-poly geometry + real panel detail, still toon-shaded with
  the inverted-hull outline.
- **Poly budget:** not answered → fidelity-first default: ~20-30k tris fighters, ~40-60k tris bombers,
  outline kept but thinned on the dense models.

## Why Blender (and not more procedural code)
Blender 5.2.2 LTS is installed at `C:\Program Files\Blender Foundation\Blender 5.2\blender.exe` and runs
headless (`--background --python <script>`); a probe that lofted a fuselage, emitted the contract nodes and
exported a `.glb` (7 KB) already works. Godot imports glTF natively and `export_presets.cfg` has
`export_filter="all_resources"`, so new `.glb` files ship without a preset change. Hand-lofted GDScript
cannot reach airfoil sections, real planforms, nacelles, turrets or canopy framing at this poly count.

## Hard rules
- **Original geometry only.** Everything is generated from published dimensions / 3-views. Never import,
  convert or trace meshes from any other game.
- **The model contract must keep passing `tools/tests.gd::_test_aircraft_models` and `_test_markings`:**
  root named `Model`, a `Body` group, a `Fuselage` MeshInstance3D with a real mesh, `Canopy`, `CockpitEye`,
  `GearL`/`GearR`, a `Pilot` in the cockpit, non-degenerate bounds.
- Keep the runtime contract too: `Propeller`, `Blades` (v5.1 prop-blur swap), `PropDisc`, `MuzzleL`/`MuzzleR`,
  `CockpitEye`, metres, **nose toward -Z**, scaled by the spec's `scale`.
- `AircraftModels.build()` keeps the procedural `PlaneBuilder`/`SpitfireModel` path as the fallback for any
  id without a generated model, so a missing asset can never break a sortie.
- Aircraft stats/physics (`data/aircraft/*.tres`) are untouched — this is geometry only.

## Pipeline
1. `tools/models/kit.py` — Blender-side geometry kit: lofted fuselage from station tables, wing/canopy from
   planform + airfoil sections, nacelles, turrets, gear legs, props/spinners, control surfaces, contract
   node emit, glTF export, ortho sheet render.
2. `tools/models/data/<id>.py` (or json) — per-aircraft published dimensions and station tables.
3. `tools/models/build_all.py` — runs the builders headless, writes `assets/models/<id>.glb`.
4. Godot side: `scripts/models/gltf_models.gd` rewires an imported scene to the contract + the toon
   materials (top/underside/patch from the spec palette) and `AircraftModels.build()` prefers it.
5. `scenes/model_gallery.tscn` + `--model-gallery` renders every model for eyeballing; tests stay green.
